# แผนพัฒนา AIUsageBar MVP — 0.1.0

จัดทำ 2026-10-03 · แผนสำหรับพัฒนาและทดลองในเครื่อง
สถานะจริงของงานติดตามที่ [STATUS](../STATUS.md); ขอบเขตและสิทธิ์ยึด [DECISIONS](../DECISIONS.md)
การเขียนแผนนี้ไม่ใช่การอนุมัติเปลี่ยนวิธีเชื่อมบัญชีหรือเผยแพร่แอป

## ภาพรวมสำหรับผู้บริหาร

สร้างหน้าปัดเล็กบน Menu Bar ของ Mac รวมยอดการใช้โควตารายสัปดาห์ของ Claude และ Codex เป็นภาษาไทย
ผู้ใช้ล็อกอินผ่านโปรแกรมของแต่ละค่าย; แนวทางที่เสนอให้แอปเราอ่านเฉพาะยอดใช้งาน ไม่รับรหัสผ่านหรือ token
ผลส่งมอบแรกคือแอปที่เปิดใช้บน Mac เครื่องนี้ได้ พร้อมผลตรวจและข้อจำกัดที่บอกตามจริง

| ลำดับ | สิ่งที่จะเห็นเมื่อจบขั้น | เกณฑ์ก่อนเดินต่อ |
|---|---|---|
| 1 | แอปเปล่าบน Menu Bar เปิดเมนูและปิดแอปได้ | build และเปิดจริงบน Mac; ยังไม่แตะบัญชี |
| 2 | ระบบข้อมูลและสถานะพร้อมรับสองค่าย | tests ของข้อมูลถูก/ผิดและข้อมูลเก่าผ่าน |
| 3 | เห็นยอด Codex จริง | อนุมัติวิธีเชื่อมและพิสูจน์ quota ของบัญชีจริงได้ |
| 4 | เห็นยอด Claude ที่ Claude Code ส่งให้ | อนุมัติโหมด snapshot; รักษา status line เดิมได้ |
| 5 | ใช้รวมสองค่ายได้โดยไม่ทำให้เข้าใจยอดผิด | ผ่านกรณี offline, login หมดอายุ, ข้อมูลเก่าและ sleep/wake |
| 6 | ชุดทดลอง 0.1.0 ในเครื่อง พร้อมส่งมอบ | review, build/test, วิธีใช้, license และข้อจำกัดครบ |

เริ่มขั้น 1–2 ได้โดยไม่รอคำตอบเรื่องบัญชี; การเชื่อมข้อมูลจริงในขั้น 3–4 ต้องรอการอนุมัติด้านล่าง
ยังไม่กำหนดวันส่งตายตัวก่อนพิสูจน์การอ่านข้อมูลจริง; หลังจบขั้น 3–4 จึงประเมินงานที่เหลือจากผลจริง

## ขอบเขตที่คงไว้

- Swift และ Apple frameworks เท่านั้น; macOS ขั้นต่ำ 14; ไม่มี dependency library ภายนอก
- Menu Bar อย่างเดียว ไม่มี Dock icon; ภาษาไทย; ชื่อ AIUsageBar ยังเป็นชื่อชั่วคราว
- แสดงใช้ไป/เหลือ/เวลา reset และสถานะของแต่ละค่าย; session quota เป็นส่วนเพิ่มเมื่อข้อมูลรองรับ
- รีเฟรชตามค่าตั้งต้นทุก 5 นาทีและกดเองได้; จำกัด request ไม่ถี่กว่า 1 นาทีตาม DECISIONS
- ไม่มีหน้าล็อกอินของเราเองในแนวทางที่เสนอ; ไม่มี analytics, telemetry หรือ auto-update
- ข้อมูลทดสอบสังเคราะห์ใช้เฉพาะ tests; แอปที่เปิดให้ผู้ใช้ดูต้องไม่แสดงตัวเลขจำลองเป็นยอดจริง

## เรื่องที่ต้องตัดสินก่อนเชื่อมบัญชี

ข้อเสนอฉบับเต็มอยู่ที่ [usage-sources](../research/usage-sources.md)

| เรื่อง | ข้อเสนอ | สิ่งที่ผู้ใช้ต้องยอมรับ / สิ่งที่ยังไม่เปลี่ยน |
|---|---|---|
| Codex | อ่าน quota ผ่าน local app-server ของ official Codex CLI | CLI อาจดูแล/refresh token ของตัวเอง; แอปเราไม่รับหรือจัดการ token ข้อยกเว้นจากกฎ no-refresh เดิมนี้ยังไม่ได้อนุมัติ |
| Claude | รับ snapshot ผ่าน Claude Code status line | เมื่อไม่ได้ใช้งาน Claude Code ยอดอาจไม่ใหม่; ปุ่มรีเฟรชอ่าน snapshot ล่าสุด ไม่ได้บังคับ server fetch |
| เชื่อมกับ Claude ที่ตั้งไว้แล้ว | helper/wrapper ของเราเลือกเฉพาะ quota แล้วคง output เดิม | เตรียมแพตช์และ backup ก่อนติดตั้ง; ยังไม่อนุมัติให้เปลี่ยน global settings ในขั้นวางแผน |

หากไม่รับข้อจำกัดของวิธีใด ให้เปิดการศึกษาเฉพาะวิธีนั้นต่อ ไม่เปลี่ยนไปใช้ token/browser cookies หรือเรียก model กระตุ้นยอดโดยอัตโนมัติ

## โครงสร้างที่เสนอ

ใช้ native Xcode project ที่เราเขียนเอง: app target และ unit-test target โดยไม่ใช้ project generator ภายนอก
บันทึก version/build number ใน build configuration แห่งเดียว; build output อยู่ใน workspace และ gitignored

| ส่วน | หน้าที่ |
|---|---|
| App | entry point, MenuBarExtra, เริ่ม/หยุด refresh และ lifecycle |
| Models | quota window, แหล่งข้อมูล, เวลาสังเกตข้อมูลและสถานะ |
| Providers | adapter ต่อค่าย, parse และแปลงข้อมูลเป็น model กลาง |
| Services | refresh coordination, process/IPC และ snapshot store ตามหน้าที่ที่จำเป็น |
| UI | ข้อความไทย, เมนูและสถานะ; ไม่อ่าน credential หรือจัดการ endpoint |
| Tests | synthetic fixtures, parser, freshness และ refresh/process failure cases |

เลือกแยกส่วนเฉพาะที่จำเป็นต่อสอง providers และการทดสอบ ไม่สร้าง framework ทั่วไปเผื่อฟีเจอร์ที่ยังไม่มี

## งานและเกณฑ์รับงาน

### T1 — แอป Menu Bar ที่เปิดได้ (M2)

สร้าง app target, minimum OS, `LSUIElement`, ไอคอนของเรา, เมนูไทย และปุ่มออก
มีแถว Claude/Codex แสดงยังไม่เชื่อม/ไม่มีข้อมูลตามจริง โดยไม่เริ่ม subprocess หรือ network ตอนเปิด

รับงานเมื่อ `xcodebuild` ผ่านและเปิด app bundle ใน workspace บน Mac ได้; เมนูเปิด/ปิด, keyboard navigation และ quit ทำงาน; ไม่มี Dock icon
บันทึกคำสั่ง build, toolchain และ smoke result ใน validation; การ build ผ่านบนเครื่องนี้ไม่เท่ากับทดสอบ macOS 14 แล้ว

### T2 — Model, parser และความสดของข้อมูล (M2 → M3)

กำหนด model กลางและสถานะ loading/available/unavailable/requires-login/failed/stale ให้แต่ละค่ายอิสระกัน
แยกเวลารับ snapshot, เวลาที่ provider ยืนยันข้อมูลและเวลาสำเร็จล่าสุด; ไม่ใช้ timestamp อ่านไฟล์แทน timestamp fetch
กำหนด freshness policy ใน DECISIONS ก่อนปิดงานนี้ โดยไม่อ้างอายุที่ server ยืนยันไม่ได้

รับงานเมื่อ tests ครอบคลุม 0/100/ทศนิยม, non-finite/out-of-range, field หาย/type ผิด, weekly window หาย, timestamp ผิดและ reset ผ่านไป
การอ่าน snapshot เดิมซ้ำไม่ทำให้ข้อมูลดูใหม่; quota ของค่ายหนึ่งผิดพลาดไม่ทำให้อีกค่ายหายไป
unit tests ไม่ต้องมีบัญชีจริงหรือเชื่อม network

### T3 — Codex: พิสูจน์การอ่าน quota จริงก่อนขยาย (M1 → M3)

ขึ้นกับการอนุมัติวิธี Codex และ T2
ตรวจ executable/version, effective configuration, network destinations และผลข้างเคียงของ app-server ก่อนใช้งานจริง
ใช้ local stdio; จำกัด RPC ที่เรียก; ไม่มี model turn, login/logout, credit reset หรือการส่งอีเมล
อ่านและเลือก weekly window จาก metadata จริง ไม่ตีความ `secondary` เป็นสัปดาห์โดยเดา
ก่อน smoke บัญชีจริง ต้องผ่าน synthetic parser, timeout/EOF และ process-lifecycle tests โดยไม่ใช้ credential จริง

รับงานเมื่ออ่านยอดและเวลา reset ของบัญชีที่ล็อกอินผ่าน CLI ได้ แล้วเทียบกับหน้าปัดของผู้ให้บริการ/CLI ที่มีอยู่
การตรวจค่าจริงทำเฉพาะในเครื่อง ไม่ใส่ account data หรือ raw responses ลง Git/log
tests ต้องครอบคลุม process ไม่พบ, timeout/EOF, invalid response และหมดสิทธิ์; process ของเราปิดได้โดยไม่หยุด session เดิมของผู้ใช้
หาก auth lifecycle หรือ side effects ไม่ตรงข้ออนุมัติ ให้หยุดเส้นทางนี้และรายงานก่อนเพิ่ม fallback

### T4 — Claude: รับ snapshot โดยรักษาระบบเดิม (M1 → M3)

ขึ้นกับการอนุมัติวิธี Claude และ T2; ทำหลังพิสูจน์ Codex เพื่อลดงานเชื่อมสองค่ายพร้อมกัน
ตรวจ version และ status-line command/script เดิมแบบไม่เปิดเผย secrets; เตรียม wrapper ที่ส่ง stdin เดิมให้ script เดิมได้ตามพฤติกรรมที่ตรวจ
helper ของเราเลือกเฉพาะ quota และ metadata ขั้นต่ำที่จำเป็น; snapshot เขียนแบบ atomic/private และอยู่นอก source tree
ไม่เก็บ stdin ทั้งก้อน, transcript หรือ credential; ไม่ให้ session เก่าหรือการสลับบัญชีทำให้ยอดถูกอ้างว่าเป็นบัญชีปัจจุบันโดยไม่มีหลักฐาน

รับงานเมื่อ parser tests ผ่านและ wrapper test รักษา output/stdin เดิมได้ รวม concurrent writes และ input ผิด
ก่อนติดตั้ง global ให้ผู้ใช้เห็น diff/backup/วิธีคืนค่าและขอ escalation ตามข้อจำกัด filesystem
หลังติดตั้ง smoke ด้วย Claude Code จริง ต้องเห็นยอดที่ส่งมาและสถานะ snapshot/stale ถูกต้อง; ไม่เปิด Keychain หรือ browser cookies
การถอน bridge คืนเฉพาะการตั้งค่าที่เราเป็นเจ้าของ โดยตรวจว่าผู้ใช้ไม่ได้แก้ทับภายหลัง; ไม่ logout หรือแก้ credential

### T5 — รวม UI และ refresh ที่ทนต่อความผิดพลาด (M4)

นำผลสอง providers มาแสดงเป็นภาษาไทย พร้อมแหล่งข้อมูลและความสด
refresh ทุก 5 นาที, manual refresh, rate-limit handling, cancellation และการกลับจาก sleep; request เก่าไม่ทับผลใหม่
ปุ่มรีเฟรชต้องสื่อให้ตรงกับวิธีของแต่ละค่าย และไม่ทำให้ผู้ใช้เข้าใจว่า Claude snapshot เป็นข้อมูลสดจาก server

รับงานเมื่อผ่าน offline/timeout/login หมดอายุ/ข้อมูลขาด/ข้อมูลเก่า/หลาย sessions/สลับบัญชีและ sleep-wake
ตรวจวันที่ตาม timezone ของเครื่อง, keyboard/VoiceOver และการตอบสนองของเมนูระหว่าง fetch
วัด CPU/memory/request count พร้อมบันทึกสภาวะและเกณฑ์ยอมรับก่อนอ้างว่าผ่าน; ไม่มี busy polling หรือ process รั่วหลัง quit

### T6 — Review และชุดทดลอง 0.1.0 (M5)

ตรวจตาม [Engineering Baseline v1](../DEVELOPMENT.md) และให้ independent review ส่วน provider/auth/data integrity
แก้ข้อผิดพลาดสำคัญก่อนส่งมอบ; ตรวจ secret, third-party notices, MIT LICENSE ของเรา และไอคอน/ชื่อ
เตรียม app bundle ในเครื่อง, README วิธี build/use, CHANGELOG, STATUS และผล validation ที่มีข้อจำกัดครบ

รับงานเมื่อ build/test/smoke ของชุดส่งมอบผ่าน เปิดใช้งานจริงได้ทั้งสองค่ายตามโหมดที่อนุมัติ และไม่อ้าง macOS/architecture ที่ยังไม่ตรวจ
เวอร์ชัน 0.1.0 เป็นเป้าหมายชุดทดลอง; ยังไม่ย้าย changelog เป็น release ที่เผยแพร่หรือ tag release จนมีการอนุมัติที่เกี่ยวข้อง
ไม่สร้าง remote/push/public release หรือ signing/notarization เพื่อแจกจ่ายจากแผนนี้

## ลำดับและการบริหารงาน

1. T1 และ T2 เป็นงานแรกที่ไม่แตะบัญชี
2. อนุมัติวิธีเชื่อม → พิสูจน์ T3 → ทำ T4 → รวม T5 → ปิด T6
3. หากวิธีหนึ่งยังไม่ผ่าน ให้เก็บ UI ของค่ายนั้นเป็นสถานะตามจริง; ห้ามปิด M3/M5 ว่ารองรับสองค่ายแล้ว
4. แบ่งชุดงานและ commit ตามผลลัพธ์ที่ review ได้; อัปเดต STATUS เมื่อจบชุดงาน และ CHANGELOG เมื่อมีผลต่อการใช้งาน/ดูแล
5. Main agent เป็นผู้รวมงานและตรวจผล; delegate เฉพาะงานอิสระที่มีขอบเขตชัดและไม่เขียนไฟล์ร่วมกัน; ไม่มี recursive delegation
6. เรื่องที่เปลี่ยนขอบเขต/ข้ออนุมัติลง DECISIONS; ผลทดสอบลง validation; แผนนี้เก็บงานที่ตั้งใจทำ ไม่ทำหน้าที่เป็น progress log ซ้ำ

## ความเสี่ยงและจุดหยุด

| ความเสี่ยง | วิธีจัดการ |
|---|---|
| API/schema หรือ CLI เปลี่ยน | adapter แยก, version/schema tests, แจ้งโหลดไม่สำเร็จตามจริง |
| Claude snapshot ไม่สด | ระบุแหล่งและอายุข้อมูล; ไม่ reset อายุเมื่ออ่านซ้ำ; ผู้ใช้ต้องยอมรับโหมดนี้ |
| CLI refresh/config มี side effects | พิสูจน์ใน T3 และทำเฉพาะขอบเขตที่อนุมัติ; ไม่แอบเปลี่ยน credential policy |
| status line เดิมเสียหรือหลาย sessions ทับกัน | wrapper tests, atomic storage, preview/backup และ ownership checks ตอน rollback |
| มีเฉพาะ Mac ปัจจุบันให้ทดสอบ | รายงาน environment จริง; macOS 14 compatibility ยังต้องมีหลักฐานก่อนรับรอง |
| พบ secret หรือข้อมูลถูกแสดงผิดบัญชี | หยุดเส้นทางที่เกี่ยวข้อง แก้และตรวจใหม่ก่อนทดลองต่อ |

แผนนี้สำเร็จเมื่อมีหลักฐานรับงานครบ ไม่วัดจากจำนวนไฟล์ เอกสาร หรือเปอร์เซ็นต์ประมาณ
